哈希表理论基础

哈希表

哈希表，Hash Table，也有叫散列表的，哈希表可以根据关键码的值直接进行访问的数据结构。数组也可以看作是哈希表，其索引就是关键码，通过下标索引访问数组元素就是哈希表访问元素的过程。一般而言，哈希表用来快速判断某个元素是否在集合里。例如给定n个学生，每个学生都有学号和姓名，如果希望实现输入学号，返回姓名的查询功能，就可以用哈希表实现。
除哈希表外，数组和链表也可以实现查询功能：

  • 添加元素：仅需将元素添加至数组（链表）的尾部即可，使用 𝑂(1) 时间。
  • 查询元素：由于数组（链表）是乱序的，因此需要遍历其中的所有元素，使用 𝑂(𝑛) 时间。
  • 删除元素：需要先查询到元素，再从数组（链表）中删除，使用 𝑂(𝑛) 时间。

    可以看到哈希表中进行增删查改时间复杂度都认为是O(1)。

2. 哈希表简单实现

首先考虑最简单的情况，仅用一个数组实现哈希表。在哈希表中，将数组中每个空位称作桶(bucket)，每个桶可以存储一个键值对，因此查询操作就是找到key对应的桶，在桶中获取value。
第一个要考虑的问题就是：如何根据key定位到桶。这一点可以通过 哈希函数 hash function实现，哈希函数的作用是将一个较大的输入空间映射到一个较小的输出空间。在哈希表中，输入空间是所有key，输出空间是所有桶（数组索引）。换言之，可以通过哈希函数得到key对应的键值对在数组中的存储位置。
输入一个key，哈希函数的计算分为两步：

  1. 通过某种哈希算法hash()计算得到哈希值
  2. 将哈希值对桶数量（数组容量）capacity取模，从而获取key对应的数组索引index

index = hash(key) % capacity

上述代码简单的根据数组实现了一个哈希表数据结构，其中hashfunc比较简单，哈希值就等于key，然后key到数组索引的映射就用了简单的取余，其他的增删查改等等都是基础操作，需要一定的代码基础，但理解不难。这里主要引申出来的问题是哈希冲突问题，可以想到上述的实现中会存在这样一个问题，假设capacity=100，根据目前的映射关系，如果存在key=115和key=215的情况，此时对100取余都是15，也就是说两个key与同一个桶位置对应，这就是哈希冲突，解决哈希冲突有常见的两类方法，一是拉链法（链式地址），二是开放寻址（线性探测、平方探测等）方式。

哈希冲突与扩容

首先通常对于哈希函数来说，输入空间一般远大于输出空间，因此哈希冲突是不可避免的，哈希冲突会导致查询错误，甚至严重影响时间效率以及可用性。为了解决上述基于数组实现的哈希表中存在的哈希冲突，最直观的方式就是数组扩容，直到哈希冲突消失。但这种方法显然效率太低，因为扩容需要大量的搬运和哈希值计算，因此首先考虑哈希表结构改良，也就是上面说的链式地址法以及开放寻址法。
【链式地址法】

基于链式地址实现的哈希表操作如下：

  • 查询元素：输入Key，经过哈希函数找到索引，即可访问链表头节点，然后遍历链表比对Key，找到目标键值对
  • 添加元素：先通过哈希函数找到链表头节点，然后将节点添加到链表中
  • 删除元素：根据哈希函数结果访问链表头部，接着遍历链表以查找目标节点并删除
    存在以下问题：
  • 占用空间增大，链表包含节点指针，相比数据更占空间
  • 查询效率低，需要线性遍历链表找对应元素

当链表很长时，查询效率会退化到O(n)。此时可以将链表转换为AVL树，或红黑树等平衡搜索树结构，这些搜索树（或跳表）结构能将搜索效率优化到O(logn)。

1. 开放寻址方法

开放寻址open addressing 不引入额外的数据结构，通过多次探测处理哈希冲突，探测方法主要包括线性探测、平方探测和多次哈希等。

  1. 线性探测
    线性探测采用固定步长探测，操作方法和普通哈希不同：

    • 插入元素，通过哈希函数计算桶索引，若桶内已有元素，则冲突位置往后线性遍历，直到找到空桶，将元素插入其中。
    • 查找元素，若发现哈希冲突，使用相同步长往后线性遍历，直到找到对应元素，如果遇到空桶，则说明目标元素不在哈希表中。

    线性探测容易出现聚集现象，具体来说，数组中被连续占用的位置越长，这些连续位置发生哈希冲突的可能性越大，从而将进一步促使该位置聚堆生长，形成恶性循环，最终导致增删查改效率恶化。（很好理解，举个例子，假设还是按照 %100计算桶索引，那么后两位数相同的key就会指向同一个桶索引，根据线性探测的定义，假设探测步长就是1，那么每次存放新值的时候，如果桶里已经有值，就会自动按照步长1往后，直到找到一个空桶存放该值，假设有一个区域，里面存放了076、077、078、176、276、277等，那么这块连续占用的区域对后两位是76、77、78的数字进行生长，这还只是数量少的情况，假设这块区域包含了更多情况，那么更这块更大概率引发哈希冲突的区域就会发生聚堆生长的现象，每个新输入key发生了与这块区域的哈希冲突，就会往下找空桶放值，由于这块区域涵盖较多哈希冲突的情况，那么更大概率值都会在这个区域往下寻找的空桶上，最终这种存放依旧没有太多规律，极大的恶化操作效率。）
    而且我们不能在开放寻址哈希表中直接删除元素，因为删除元素后会产生一个空桶，而查询元素时，线性探测遇到空桶就会返回，因此在该空桶后的元素都无法访问，可能误判。


为了解决这个问题，可以采用懒删除机制，不直接从哈希表中移除元素，而是利用一个常量TOMBSTONE标记这个桶，该机制下None和TOMBSTONE都能表示空桶，都可以放置键值对。但线性探测遇到TOMBSTONE标记时可以继续遍历。这种方式会加剧哈希表的性能退化，因为线性探测可能会跳过多个TOMBSTONE标记才能找到目标元素。
因此可以考虑在线性探测过程中记录遇到的首个TOMBSTONE索引，然后将搜索到的目标元素与TOMBSTONE交换位置，这样做每次都能将元素移动到距离起点更近的位置，优化查询效率。

2. 平方探测

平方探测和线性探测类似，发生哈希冲突时，平方探测不是简单的跳过一个固定步数，而是跳过探测次数的平方的步数，即 1 4 9 16..步。平方探测的优势在于能够缓解聚集效应，有助于数据分布的更加均匀。当然这种设计也存在问题，一是聚集现象仍旧存在，二是平方探测可能导致哈希表中有空桶，无法访问到。

3. 多次哈希

多次哈希方法使用多个哈希函数f1(x) f2(x) f3(x)… 进行探测。

  • 插入元素， 若哈希函数f1(x)出现冲突，尝试f2(x)，以此类推，直到找到空位插入元素
  • 查找元素，在相同的哈希函数顺序下进行查找，直到找到目标元素返回；若遇到空位或已经尝试了所有哈希函数，说明哈希表中不存在该元素。

不同的编程语言使用了不同的哈希表结构优化策略，例如Python采用开放寻址，字典dict伪随机数探测，Java采用链式寻址，HashMap内数组长度达到64，且链表长度达到8时，链表转换为红黑树提升查找性能。Go采用链式地址，Go每个桶最多存放8个键值对，超出容量则连接一个溢出桶，溢出桶过多时会执行一次特殊的等量扩容操作。C++中则同样使用链式地址法。

哈希算法

无论是链式寻址还是开放寻址，只能保证哈希冲突时哈希表仍能够正常工作，但无法减少哈希冲突的发生，而哈希算法直接影响到了键值对分布。
index = hash(key) % capacity
当哈希表容量固定时，hash()哈希算法决定输出值，为了降低哈希冲突发生的概率，设计一个鲁棒的hash()也是比较重要的选择。

哈希算法的目标

哈希算法应当具备：

  • 确定性：对于相同输入，哈希算法产生相同输出
  • 效率高：计算速度尽量快，计算开销小
  • 均匀分布：哈希算法应当使键值对均匀分布在哈希表中，分布越均匀，哈希冲突概率越低。
    除了应用在哈希表中，哈希算法还广泛应用到：
  • 密码存储：为了保护用户密码安全，系统通常不会直接存储用户的明文密码，而是存储密码的哈希值。
  • 数据完整性检查：数据发送方可以计算数据的哈希值一并发送，接收方可以重新计算数据的哈希值进行比对。
    对于密码学的相关应用，为了防止从哈希值反推出原始密码等逆向工程，哈希算法需要具备：
  • 单向性：无法通过哈希值推导出关于输入数据的任何信息
  • 抗碰撞性：极难找到两个不同的输入对应相同输出
  • 雪崩效应：输入的微小变化应到导致输出变化显著且不可预测

哈希算法的设计

简单的哈希算法例如 加法哈希、乘法哈希、异或哈希、旋转哈希。

上述每个算法最后都对一个很大的质数1000000007取模，以确保哈希值在一个合适范围。对质数取模有一个重要原因：使用大质数作为模数，能最大化保证哈希值的均匀分布。 因为质数没有与其他数字存在公约数。

常见哈希算法

当然上述简单哈希算法依旧存在问题，在实际应用中，通常会用到一些标准的哈希算法包括 MD5、SHA-1、SHA-2、SHA-3等。可以将任意长度的输入数据映射到恒定长度的哈希值，

哈希表底层实现是数组、链表、二叉树，为什么其效率能比他们更高呢？
哈希表的时间效率变高，但牺牲了部分空间效率，哈希表中相当一部分内存没被使用。其次只是在特定场景下时间效率变高了，如果一个功能能够在相同场景下使用数组或链表实现，那么一般会比哈希表更快，因为哈希函数计算开销，时间复杂度常数项更大。而且哈希表的时间复杂度可能劣化，比如链式寻址中，如果分布不好，哈希冲突严重时时间复杂度退化到O(n)。

哈希表相关代码题

242. 有效的字母异位词

力扣题目链接
给定两个字符串 s 和 t ，编写一个函数来判断 t 是否是 s 的字母异位词。
示例 1: 输入: s = “anagram”, t = “nagaram” 输出: true
示例 2: 输入: s = “rat”, t = “car” 输出: false
说明: 你可以假设字符串只包含小写字母。

思路： 简单的暴力思路就是第一层循环遍历字符串s，对每个s的字符，可以再嵌套一层循环，遍历t中是否存在该字符，同时要记录字符是否重复出现，或者记录字符数量来作辅助判断等等，相当麻烦。这题通过哈希表就能快速解决，直接一点的解法就是直接建立一个map，遍历s中的字符，统计每个字符数量，然后在遍历t字符串，将t中的字符当作key，查询到的key对应的value–，最后检查哈希map中是不是所有值都等于0，如果是就满足题目要求。
当然数组也是一种哈希表，而且这道题目中的字符串只有小写字符，也就是限定了范围，因此可以借助数组来存储字符出现的次数，这个操作在字符串相关的题目中经常会出现：用s[i] - 'a'来计算索引，这样就把26个小写字符映射到了0-25的数组索引。

349. 两个数组的交集

力扣题目链接

这题简单，主要是元素唯一怎么实现，其实unordered_set就可以实现了，并且不需要考虑输出顺序，对于限制数值大小的题目，可以用数组来做哈希表，但这道题没有限定数值，就无法用数组来做了，否则可能造成空间浪费。
对set结构来说，C++提供了std::set std::unordered_set std::multiset三种，set和multiset都是基于红黑树实现的，所以有序。unordered_set基于哈希表实现，所以无序，但其读写效率最高。因此本题使用unordered_set即可。

202. 快乐数

力扣题目链接
编写一个算法来判断一个数 n 是不是快乐数。

「快乐数」定义为：对于一个正整数，每一次将该数替换为它每个位置上的数字的平方和，然后重复这个过程直到这个数变为 1，也可能是 无限循环 但始终变不到 1。如果 可以变为  1，那么这个数就是快乐数。
如果 n 是快乐数就返回 True ；不是，则返回 False 。

示例：
输入：19
输出：true
解释：
1^2 + 9^2 = 82
8^2 + 2^2 = 68
6^2 + 8^2 = 100
1^2 + 0^2 + 0^2 = 1

思路： 循环计算sum，用一个哈希集合存放sum，如果某次循环检测到sum已经存在，说明出现了无限循环，直接返回false，如果最终sum=1，那么返回true。

【拓展】本题也可以用快慢指针法，当出现循环就等同于出现了环，而判断有无环 快慢指针是最常用的方式。这种写法空间复杂度能到O(1)，而且这个写法比较帅。

1. 两数之和

力扣题目链接(opens new window)

给定一个整数数组 nums 和一个目标值 target，请你在该数组中找出和为目标值的那 两个 整数，并返回他们的数组下标。
你可以假设每种输入只会对应一个答案。但是，数组中同一个元素不能使用两遍。
示例:
给定 nums = [2, 7, 11, 15], target = 9
因为 nums[0] + nums[1] = 2 + 7 = 9
所以返回 [0, 1]

思路： 暴力解法就是两层for循环，时间复杂度O(n^2)。而且这道题可以可以借助哈希表来减少时间复杂度，因为哈希表查询的时间复杂度是O(1)的，借助哈希表，将遍历过的元素 索引和值存放到哈希表中，然后在后面的遍历中，每次询问哈希表中是否存在 target - num，若存在，则返回下标。因为这道题要记录下标，所以用unordered_map，unorderer_set只能存放key，不能存放value。对unordered_map而言，C++中也支持std::map std::multimap std::unordered_map三种，且map和multimap都是底层由红黑树实现的，unordered_map底层由哈希表实现。

454. 四数相加

力扣题目链接

思路： 这题有点像两数之和的升级版。本题当然不可以用四重暴力循环来做，时间复杂度太高，考虑使用哈希表优化查询，首先用一个哈希Map统计A和B中所有元素相加结果的次数，然后在遍历C和D，找到C+D+A+B = 0情况并统计次数，此时哈希表的优势体现出来，当0 - （C+D)在哈希表中存在的话，就直接计数加上哈希表对应的值即可，因为这意味着存在这么多个A+B的组合满足A+B+C+D=0。
