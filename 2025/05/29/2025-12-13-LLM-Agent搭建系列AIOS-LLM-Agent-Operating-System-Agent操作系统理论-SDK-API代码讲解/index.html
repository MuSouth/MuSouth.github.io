【LLM-Agent搭建系列】AIOS-LLM Agent Operating System （多Agent操作系统）理论+SDK API代码讲解

MuSouth
2025-05-29 (Updated: 2025-12-13)
LLM-Agent
LLM-Agent, RAG

前言

Agent以LLM为大脑，并拥有理解指令、信息处理、任务规划、工具调用等等能力，这是目前Agent的核心定义。当下基于LLM的Agent开发如火如荼，但大多是针对Agent本身能力，例如通过各种各样的工具函数丰富Agent的能力，通过构造各种丰富的提示词来使得Agent做到更好的意图理解与任务拆解，但很少有工作针对Agent在资源使用上作优化。
这个需求其实来自于如下场景：当我们定义了一个智能体，该智能体假设可以正常工作，正常解决用户需求，那么我们就不太需要对其做什么改进了，只要减少LLM的调用成本，或者在其他外部工具的调用效率上下文章就可以了。但总有些工作复杂程度高，在同一台机器上也不一定只跑一个Agent，可能同时存在多个Agent，扮演不同角色，就好像有不同流水线上的工作人员，有的负责网络资源调取整理，有的负责查阅论文资料总结，有的专门负责模仿写作等等，当多个Agent在同一个机器上运行，他们可能调用同一个LLM，可能使用相同的工具。随着任务变多，智能体数量变多，其复杂性就会快速上升，而LLM和操作系统可能只有一个，这就给操作系统和LLM带来了挑战。在有限LLMs服务资源中，假设单个LLM，以及单个操作系统，运行多个Agent就会出现以下场景：

  1. 智能体请求LLM的调度优化和资源分配，哪个Agent优先调用LLM或其他工具？
  2. 智能体在与LLM交互中的上下文维护，尤其是上下文很长，LLM生成速度变慢，耗时增强。
  3. 不同能力Agent集成带来的复杂性问题，某些Agent生成被暂停，怎么快照保存当前结果
    面对以上问题，AIOS搞了一个Agent操作系统，「AIOS旨在优化资源分配，促进Agent之间的上下文切换，实现Agent的并发执行，为Agent提供工具服务，并维护Agent的访问控制」 。结构图如下：

AIOS应用层

在应用层，可以开发和部署智能体应用程序。在这一层，AIOS提供了AIOS SDK，对系统调用进行了更高级的抽象，从而简化了智能体的开发过程。该SDK通过提供丰富的工具包，来抽象低层系统功能的复杂性，使开发者可以专注于智能体的基本逻辑和功能，从而提高开发效率。

AIOS内核层

内核层分为操作系统内核以及LLM内核，原始OS内核负责硬件管理，处理无智能软件的请求，而新增加的LLM内核则专用于处理与LLM智能体、LLM相关资源和开发工具包相关的职责。

Agent调度器

优化LLM资源使用，通过FIFO、RR等调度算法优先处理和调度Agent请求。

原本对多个Agent的调度是上面那样，处理完一个Agent的所有请求后才会对下一个Agent请求响应，而Agent调度器的引入会改善这种情况，避免部分有时限的Agent饿死。调度方案采用FIFO（First in First Out）以及轮询（RR, Round Robin)的方式，论文没有提出新的策略，这些调度方案是传统内核中常用的。

上下文管理器

支持LLM 上下文快照和恢复，以及管理LLM上下文窗口。

因为调度算法的存在，可能随时切换Agent进程，假设一个Agent的LLM请求响应时间过长，可能还没有执行完就会被强制切换，此时需要一个机制来保存LLM生成过程的状态，确保资源再度使用时能快速准确的恢复。具体来说，AIOS在上下文管理器中提供了快照和恢复机制，LLM生成响应的时候是一个一个词生成，每生成一个词的时候是针对一个词生成一个序列，然后采样，这个过程是一个搜索树，节点代表生成的词，边代表抽样概率，生成过程的快照需要存储的不仅仅是当前已经生成的序列，还要包括这个搜索树的状态：每一条边对应的概率和中间节点等等。
且上下文窗口大小有限制，这个受限于LLM的能力，比如有的Token长度在8K，有的更长能到2M甚至4M，为了超过上下文窗口，上下文管理器尝试通过其他技术在不改变LLM本身的前提下尽量扩展，这里AIOS提供了文本摘要等扩展上下文窗口的技术。

内存管理器和存储管理器

内存管理器为每个Agent交互日志提供短期内存，数据在Agent活跃时可访问，也就是说AIOS独立的存储每个智能体内存，其他智能体需要管理器授权才可以访问每个智能体的内存，内存管理器可以快速进行数据检索和处理。
而存储管理器负责数据长期存储，通过文件、数据库或云存储的方式。

工具管理器

管理一系列工具，包括网络搜索、数据库检索、图像处理等等，可以通过API的方式定义工具，也可以自己设计工具，而最新版的已经开始支持MCP的方式写服务。

访问管理器

通过为每个Agent管理专门的权限组来协调不同Agent之间的访问控制操作。被排除在智能体的权限组之外的其他智能将被拒绝访问其资源，如交互历史。访问管理器会维护审计日志。这些日志记录了访问请求、智能体活动以及对访问控制参数的修改信息。

AIOS硬件层

CPU、GPU、内存、磁盘、外围设备等组成，硬件系统由操作系统管理，LLM层仍然调用OS提供的底层接口。

AIOS内核代码框架


LLM Cores以统一方式封装了来自不同供应商的LLM实例，这种接口抽象允许通过单一接口集成多个LLM，包括使用API的方式以及本地Ollama或vLLM部署的方式。
Context Manager 负责在处理每个LLM核心时处理上下文（上下文切换等），对于CPU进程或线程来说，上下文可能是每个进程或线程的私有数据（寄存器或计数器等），对于LLM Cores来说，上下文其实就是主动输入到LLM Cores的数据，这里可能包括了对话文本数据、工具等等。
Memory Manager 内存管理器处理Agent在运行时所需的RAM数据存储，将其与持久存储区分开来。此处的“内存”指的是为了持续操作所必需的瞬态数据，例如临时变量或最近处理的数据。它支持Agent在执行活动任务期间快速存储和检索信息所需的内存操作。
Storage Manager 存储管理器旨在处理持久存储操作，其中“存储”是指Agent可能在未来任务或日志记录中需要的保存在磁盘上的数据。
Tool Manager 工具管理器加载和管理AIOS-Agent SDK中可用的各种工具。该模块管理工具调用冲突，并优先处理工具操作，以确保工具调用的稳定执行。

关于Kernel里的接口函数，或主要函数，这里不再详细介绍了，可以参考官方文档。

AIOS+Cerebrum如何运行和开发Agent

环境配置注意事项

安装和配置AIOS环境时要确保python版本和官方要求一致，目前版本建议为3.10-3.11（python版本建议就选择3.10，避免项目构建时一些依赖不兼容高版本python），Cerebrum的python版本一致，不过执行pip install -e .命令安装该库时，解析pyproject.toml一步其实有点问题，首先这个包通过hatchling来打包的，所以其后端需要hatchling来构建编译，在执行安装命令前记着pip install hatchling，然后注意这个toml文件里有两行关于LICENSE的配置，安装这个包时会检测这个所谓的LICENSE文件，但实际上项目里并没有这个文件，你down下来的文件目录下不存在，可以把这两行关于LICENSE验证的语句删除，接下来执行pip install - e .就可以正常进行了。

这里其实推荐用uv作包管理，所以上述pip install 可以统一用uv pip install 替代，使用uv前首先在项目目录下执行uv venv，然后source .venv/bin/activate 就可以激活环境了，用uv作依赖管理现在很流行，而且uv下载的包都在当前目录下很好找，而且其层级结构安排的比较简洁，调用关系一目了然，不像conda那样相对来说比较复杂。

上面的坑都踩完后，接下来就是简单的按照官方git仓库下的指引，把requirement.txt里列好的依赖都装好，就可以试着开始运行了。

SDK API详解

其实在上一小节的简单应用示例中，已经初步调用了一些API用来构建Agent，下面就API功能进行讲解，方便后续开发参考。

【Memory API】

Memory API 提供了一种结构化的方式管理和检索Agent Memory，通过CRUD操作和语义搜索到方式，所谓的Memory对象在这里指的是文本信息、MetaData、Memory ID，对于每个Agent都会在自己的命名空间内维护自己的内存空间。

【Storage API】
这套API接口用来和主机文件系统交互，涉及到装载、检索、创建文件、修改和共享文件等等，这个目的大概是为了持久化一些缓存数据。比如一些对话数据，可以保存到某个目录下，后面重启对话时可以作为历史对话数据采纳。
这边就不再一个一个讲解接口函数了，在官方文档中有使用示例。

【Tool API】
这个工具相关的API，包括download-tool、upload-tool是为了方便工具管理，但现在MCP更好用，AIOS其实是一个不怎么成熟的社区生态，所以它的支持并不像MCP这么完善。这些理解就行。

小结

初看名字，容易理解为AIOS在操作系统中结合了LLM或Agent，但实际上并没有对OS作改动，并非我们理解的在内核中嵌入了LLM，以结合大语言模型的能力优化调度，而是以针对Agent引入一层中间层的形式，它依旧是一种库，这个库定义了Agent上下文切换、记忆存储管理等等功能，以及Agent调度器层面上的优化，从而通过并行运行多Agent时的以减小阻塞时间等。理解了AIOS的基础原理，本文其实主要是分享AIOS基本概念和怎么使用AIOS进行开发，AIOS的概念找到了几篇写的不错的文章，主要理论讲解也是参考的几篇知乎文章，链接都放在下面了，而开发文档我查阅了很久，发现中文互联网上并没有太多的相关资料，也不知道是不是查阅的姿势不对，所以我这边就研究了研究，跟着开发文档把这个项目的开发链路摸透了，并且用一个demo作演示。

当前构建一个Agent，可以用的工具很多，LangChain、AutoGen等等，或者可以用Dify等可视工具直接编排工作流。而AIOS主要想解决的是多Agent并发问题，整体上还是一个很有意思的工作。
