一、前言

学习小型LLM训练的目的是为了更好的掌握LLM原理，从实践出发体会LLM各组件的效用。NanoGPT是Andrej Karpathy 23年开源的一个GPT2规模的LLM教程项目。注意，原始的NanoGPT是经典GPT-2结构的复现，而更现代化的LLM中的技术并没有集成在原项目代码中，本次只完整记录Karpathy在视频教程以及build_NanoGPT项目中实现的过程，而将在下一篇文章综合实现结合现代化LLM技术（RoPE、MLA、GQA、RMSNorm、SwiGLU等等）的新NanoGPT，先附上Karpathy的nanogpt源代码仓库链接和build-nanogpt。build-nanogpt是相对更新的一个项目，其项目结构很简洁：train_gpt2.py里定义了模型以及训练和验证代码，fineweb.py里写了下载fineweb数据集的脚本，hellaswag.py写了一个经常被用来作验证的数据集的相关脚本。其精华就在train_gpt2.py里了。不得不说这个视频教程真的让人兴奋，karpathy行云流水的操作以及对整个模型结构和训练Pipeline的思路之清晰让人佩服。
本文主要就train_gpt2.py进行代码讲解，一方面掺杂着自己的理解，一方面在分析的过程中将Karpathy配套视频中涉及到的一些细节一并记录下来（这部分零零散散可能有些杂乱）。PS : 整个近4小时的视频，讲解的相当全面了。

三、Dataloder和Tokenizer

Tokenizer

数据和模型是两大基本盘，模型的定义我们已经在上节总结过了，下面主要是数据加载器的定义和分词器的定义。自然语言从输入到llm输出一般经历如下过程：

  • Tokenizer分词，将输入自然语言sequence转化为token，数值范围在0 到 vocab_size
  • 从vocab_size大小的idx索引列表->embedding层，嵌入表维度(vocab_size, embedding_size)
  • 索引列表转为为(seq_len, embedding)维度，也就是从vocab空间映射到了embedding空间
  • 经过多层transformer块计算，维度不变
  • 最后通过输出头，也就是一个线性层，维度映射回vocab_size，最终输出(seq_len, vocab_size)
    此时最后一个长度为vocab_size的向量代表着下一个词的分布，采样该分布得到下一个token
  • 用tokenizer将token转换回文本输出

在转换为vocab之前会先进行分词，常用的分词策略包括Byte Pair Embedding, BPE、WordPiece和Unigram Language Model，对不同语料库以及不同大语言模型构建的词表数量，相关内容后面专门总结一期。对GPT2而言，Vocab_size为50257，50257=50000+256+1（50000个词元，256包含扩展ASCII，最后一个endoftext，作文本结束符。

Dataloader

此外如何从数据集中加载数据，构建训练用的dataloader也是一个关键步骤。因为大语言模型推理的过程，或者说Decoder推理过程中，只会用T个token中最后一个token对应的logit作softmax以预测下一个词，而不是全部T个token的logits，因为第T个token已经聚合了整个输入序列的信息，事实上Attention计算被认为具有聚合信息的能力，MLP则没有这种能力。第T个token输出综合了整个输入序列，大致的计算流程如：
模型输入：x=[x1,x2,x3]，
模型输出：logits (1, 3, vocab_size)
基于x1预测x2分布的logits[:, 0, :]
基于x1,x2预测x3分布 logits[:, 1, :]
基于x1,x2,x3预测next分布logits[:, 2, :]
简而言之，预测下一个的范式：对logits[:, -1, :]取softmax就得到了下一个词的概率分布。

这是这类自回归生成式模型的特性，尤其是对于因果编码器，只能和自身以及自身之前的token作注意力计算，这种前向推理时的自回归过程更加明确。而这个特性也正是现阶段PD分离和KV Cache的实现基础。考虑到我们在构建数据集时，模型始终以预测下一个token为目标，简单代码实现如下：

在GPT2训练中，学习率有一个warmup的过程，这个过程预设了warmup_iters，在训练批次没有达到warmup_iter之前，学习率线性增长，到达warmup设定步数后，使用余弦衰减的方式计算学习率，系数会从1到0，直到学习率衰减到最小值，如果训练步数大于最大步数，直接返回最小学习率。曲线大概就像下面这张图里展示的：

此外可能GPT2训练策略中，还涉及到了对batch_size的动态修改，比如到达预设训练epoch之后，batch_size变大，一开始用小batch，到后期batchsize不断变大，但这个改进会增加复杂度，karpathy没做。

对于大权重来说，其受到的惩罚越大，进而防止了过拟合。

梯度累积以在算力有限情况下用更大batch_size

假设总批大小为 N 。 梯度累积是一种训练技巧，用于在内存受限的情况下扩大 batch size。基本思路是在多个 mini batch 上累积梯度，达到预定义的梯度累积次数再进行一次参数更新。使用梯度累积的等效批大小——总批大小 total_batch_size = B * T * grad_accum_steps。 其中：

意思是，假设我们的设备最高只能承载B=32的情况，但我们想增大batchsize到64，此时我们在B=32的情况下计算梯度，但是这次计算后不进行反向传播，而是再计算下一个batch的数据的梯度，最后两个batch的梯度加起来，一起进行反向传播更新模型参数，这就实现了一种时间换空间的trade-off。

这其实是在分布式情况下进行梯度累积计算，实现复杂度又高了一层。对于分布式训练而言，使用torch.nn.parallel即可。

DDP 部分参数：

  • node: 概念，表示物理节点，就是一台机器，节点内部可以有多个 GPU(一台机器有多卡)。
  • RANK：表示全局进程的序号，用于进程间通信。每一个进程对应一个 RANK。RANK=0 的进程就是主进程。
  • LOCAL_RANK： 指在一台机器上（一个node上）进程的相对序号。单机多卡时，RANK 就等于 LOCAL_RANK。
  • WORLD_SIZE: 全局（一个分布式任务）中 RANK 的数量（所有进程的数量）。
  • NPROC_PER_NODE：每个物理节点上面进程的数量。

DDP 的工作模式：

  • 每个 gpu 都有自己独立的模型和数据加载器，前向传播、计算梯度、反向传播与其他 gpu 独立。
  • 反向传播就是在计算每一个参数的梯度，但此过程不做更新，直到 optimizer.step() 才更新参数。
  • 如果 model.require_backward_grad_sync=True ，那么在反向传播 loss.backward() 的时候，DDP 使用 all-reduce 操作来同步所有进程（gpu）的梯度：对所有 gpu 上梯度的做平均（也可以其他模式，基于不同的配置），然后回传给所有的 gpu，保证所有 gpu 上的梯度一致。梯度同步通过 Ring-All-Reduce 算法实现。
  • 一旦所有 gpu 上梯度都同步完成，就开始做参数更新。由于每个 gpu 都使用相同的更新梯度，故所有的模型副本在任何时间点上访问都是相同的。
  • 参考 cnblog。

分布式训练需要修改初始化、数据加载器、训练梯度同步等。这部分详情参见原视频和参考中的博文，这里不再详细赘述。不过这块倒是可以学下NCCL通信机制，因为在分布式训练中，数据的同步广播、切片等都有对应的通信原语支持，例如场景的all_reduce、scatter、all_gather等，这个是分布式训练的底层机制。

优化点2 torch.compile()编译模型

Introduction to torch.compile — PyTorch Tutorials 2.7.0+cu126 documentation
torch.compile()做的事情包括：

  • 把整个模型网络编译为一个不需要Python 解释器参与的对象
  • 更多片内操作，大量减少GPU上显存和计算单元间的load和store
    torch.compile()在分布式情况下会出现编译错误，而且输出一堆看不懂的信息，这个被Karpathy也吐槽过，这也是llm.c出现的直接原因，因为torch生态下搭建一个网络，然后对训练做优化，很多时候都是在封装好的函数使用的，底层的作用机理和调用关系很复杂，一层层的抽象可能导致结构臃肿。事实上实现一个GPT2类语言模型的训练没有那么困难，所需要的也就是数据+模型+梯度传播。llm.c用c+cuda完整实现了nanoGPT的训练，这个可以好好学习下。
    不过torch.compile()后，模型训练加速很明显，正是因为它剥离了python解释器，避免了每次训练时，在Python解释器中，一行一行阅读指令执行指令的过程。

优化点3 Flash Attention使用


FlashAttention使用切片技术，避免在相对较慢的GPU HBM上物化materialization大的NxN注意力矩阵，而是在外部循环中，遍历K和V矩阵块，将他们加载到速度较快的SRAM中，每个块内，循环遍历Q矩阵块，将他们加载到SRAM中计算注意力，最后写回HBM。整个过程还是蛮复杂的，这里并没有完全讲清楚，因为我后续会针对FlashAttention系列再总结一篇文章。

优化点4 （Nice Number）比较抽象的一个东西

计算机世界中，2的幂数 2、4、8、64、128…这些都是好数，而质数比如13 、17等就没那么优美，这个在我们设置batch_size时经常会发现，通常我们会设定为2的幂数，
因为在CUDA中，很多时候都会以2的幂数形式编写kernel，很多大小为16或64的block，当我们的输入不是nice number，可能会在CUDA中有额外的逻辑处理，反而会增加处理时间。
这里最有趣的一个改动是vocab_size从50527修改为了50304，50304=2^7 x 3 x 131，可以被2的部分幂数整除，这一步改动相当于在embedding层添加了额外的虚假token，因为这里单纯是为了凑出来一个nice number，实际数据预处理后vocab_size没那么多，但实际上因为这些虚假token在数据中从未出现，在训练过程中不会被访问，所以这些额外的列在最后一层lm_head之后，数值上会被逐渐推向很大的负值，从而在softmax后概率接近0。所以在功能上不会影响，但仅仅因为将这个值从50527这个不太好的数，变成了50304这样的nice number，token吞吐量反而变大：
